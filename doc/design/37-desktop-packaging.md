# ADR — Desktop packaging (issue #37)

**Status:** implemented (platform smoke and signed releases pending secrets)
**Date:** 2026-11-23

## Context

The desktop shell (#32), Settings (#33), audio diagnostics (#34), model manager
(#35) and onboarding wizard (#36) are implemented, but the app is still a
development/QA surface. Packaging must produce installable macOS and Linux
bundles, sign/notarize macOS, add automatic updates, and keep CI building them.
The Control API currently binds `0.0.0.0`, which is correct for companions and
headless use but too broad for a packaged desktop install.

## Decisions

1. **AppImage is the primary Linux package; `.deb` is secondary.**
   Although the daily-driver host is Debian-based, Tauri's updater on Linux
   updates AppImage only. Therefore AppImage is the path that satisfies the
   in-app updater acceptance criterion. The `.deb` is also published for native
   Debian/Ubuntu integration, but its updates are package-manager/manual rather
   than in-app. Fresh-install QA must validate FUSE and the real runtime
   dependencies (`ldd`, audio, WebKitGTK) rather than relying on a historical
   package list.

2. **macOS ships separate Apple Silicon and Intel bundles.**
   CI builds `aarch64-apple-darwin` on `macos-latest` and
   `x86_64-apple-darwin` on `macos-15-intel`. There is no universal binary.
   The desktop sidecar does not compile `parakeet`, so the Intel desktop target
   is viable even though the CLI release intentionally omits Intel macOS.
   Linux packaging is x86_64; Linux ARM remains future work.

3. **Desktop follows the daemon release tag; there is no independent cadence.**
   Every `vX.Y.Z` tag publishes the CLI artifacts plus desktop bundles. The tag
   version and the four manifests must match; `scripts/check-release-version.mjs`
   enforces this before builds run.

4. **Stable and preview updates use separate feeds.**
   Stable builds check `releases/latest/download/latest.json`. Alpha, beta and
   rc builds check the rolling technical release `desktop-updates-preview`.
   Each versioned release also uploads its signed `latest.json`; the publish job
   validates platform entries/signatures and copies it to the preview feed. This
   prevents a prerelease from becoming a required update for stable installs.

5. **Updater keys are separate from Apple signing.**
   The Tauri minisign public key is committed in `tauri.conf.json`. The private
   key and optional password live only in GitHub secrets
   (`TAURI_SIGNING_PRIVATE_KEY`, `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`). They are
   generated once and must be backed up; regenerating them invalidates future
   updates. `createUpdaterArtifacts` is enabled only by `tauri.release.conf.json`
   so local and PR builds do not require the private key.

6. **macOS uses Developer ID signing, hardened runtime and notarization.**
   `tauri-action` signs inside-out, including the sidecar, and notarizes/staples
   when Apple credentials are present. No App Sandbox or extra entitlements are
   added until a signed smoke test proves they are needed; the existing
   microphone/speech usage strings remain in `Info.plist`.

7. **Packaged desktop pins the Control API to loopback.**
   The shell sets `CONTROL_HOST=127.0.0.1` for the sidecar. The daemon default
   remains `0.0.0.0` so the CLI, headless deployments and LAN companions are
   unchanged.

8. **Update checks are automatic; installs are explicit.**
   Release builds check for an update after startup and show a banner. The user
   chooses "Install and restart", sees download progress, and the app relaunches
   through `tauri-plugin-process`. Development builds do not call the feed.

9. **Kokoro ships its espeak-ng data as a Linux resource.**
   `build-sidecar.sh` stages the espeak-ng-data generated by `espeak-rs-sys`.
   The Linux bundle copies it as a Tauri resource and the shell sets
   `PIPER_ESPEAKNG_DATA_DIRECTORY` to that resource root. This avoids relying on
   a system `espeak-ng-data` path inside an AppImage.

## Artifacts

| Platform | Artifacts |
|----------|-----------|
| macOS Apple Silicon | signed/notarized `.dmg`, `.app.tar.gz` + `.sig` |
| macOS Intel | signed/notarized `.dmg`, `.app.tar.gz` + `.sig` |
| Linux x86_64 | AppImage + `.AppImage.sig`, `.deb` + `.deb.sig` |
| CLI | macOS ARM and Linux x86_64 tarballs + SHA-256 |

The updater manifest contains `darwin-aarch64`, `darwin-x86_64`,
`linux-x86_64` (AppImage) and `linux-x86_64-deb`; the release job rejects a
publish if any platform, versioned URL or signature is missing.

## Required secrets

- `APPLE_CERTIFICATE`, `APPLE_CERTIFICATE_PASSWORD`, `APPLE_SIGNING_IDENTITY`
- `APPLE_ID`, `APPLE_PASSWORD`, `APPLE_TEAM_ID`
- `KEYCHAIN_PASSWORD`
- `TAURI_SIGNING_PRIVATE_KEY`, `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`

Without the Apple or updater secrets, unsigned/smoke builds still work, but the
issue cannot be closed.

## Verification

- PR CI: frontend checks/tests, Rust tests/clippy, unsigned Linux bundle smoke,
  structural bundle verification.
- Tag CI: version guard, per-target sidecar build, signed/notarized bundles,
  updater signatures, manifest validation, release asset validation.
- Manual: fresh macOS install + TCC allow/deny/reset, fresh Debian/Ubuntu
  AppImage/`.deb` install, updater rehearsal N → N+1, config/model/onboarding
  state preserved after update, and `make qa` green for the CLI/TUI.
